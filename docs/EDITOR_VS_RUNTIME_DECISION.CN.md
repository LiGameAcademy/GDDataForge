# GDDataForge：编辑器扩展 vs 运行时编辑器 决策文档

## 1. 问题定义

我们需要明确“数据可视化编辑能力”应该放在哪里：

- 方案 A：Godot 编辑器扩展（EditorPlugin）
- 方案 B：游戏运行时编辑器（Runtime UI）
- 方案 C：双端并存（共享核心数据管线）

## 2. 关键判断标准

- 目标用户是谁：策划/程序/玩家？
- 需要在发布版中开放编辑能力吗？
- 是否要求在线改表、热修复、远端配置？
- 安全边界：玩家是否能修改本地数据？

## 3. 结论（推荐）

建议采用**方案 C：双端并存，但共享一套核心管线**。

- **编辑器扩展**：主要服务开发期生产力（建表、批量编辑、校验、导入导出）。
- **运行时编辑器**：仅在确有需求时提供（GM、调试工具、LiveOps 配置）。
- **底层核心**：解析/序列化/缓存/资源构建必须共享，避免双逻辑分叉。

## 4. “两者是否本质一样” 的回答

从 Godot 底层看，并不完全一样：

- EditorPlugin 运行在编辑器进程，依赖 `@tool` 与编辑器 API（如 `EditorFileDialog`）。
- Runtime Editor 运行在游戏进程，依赖游戏 UI 与运行时权限模型。

但从“数据生命周期”看，两者应该共用同一个领域核心。

换句话说：

- **外层 UI 不同**
- **内核数据管线应相同**

## 5. 何时优先做运行时编辑器

满足以下至少一条再做：

- 需要在发布版直接调参（运营/活动）。
- 需要远程配置下发并即时生效。
- 有 QA/GM 在运行态操作数据的强诉求。

否则优先打磨编辑器扩展，收益更高、风险更低。

## 6. 产品分层建议

### 6.1 开发期（默认）

- 保持 EditorPlugin 为主入口。
- 提供完整建表、校验、导入导出、模型关联能力。

### 6.2 调试期（可选）

- 在 Debug 构建下提供轻量运行时面板：
  - 浏览表
  - 搜索
  - 单行改值
  - 回滚

### 6.3 发布期（谨慎）

- 若上线运行时编辑：
  - 必须加权限与签名校验
  - 明确哪些表可编辑
  - 可观测与审计（日志）

## 7. 技术落地路线（与架构文档配套）

1. 先完成 `UNIFIED_DATA_PIPELINE_ARCHITECTURE.CN.md` 的 core 层。
2. 编辑器先接 core，跑通稳定版本。
3. 再根据需求评估是否实现 Runtime 面板。

## 8. 决策记录（当前）

- 当前阶段：以编辑器扩展为主。
- 当前结论：不立即重做运行时编辑器。
- 当前动作：先统一数据管线，消除双维护。
